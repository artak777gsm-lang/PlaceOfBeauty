# CLAUDE.md

Контекст проекта для сессий Claude Code. Общая информация о запуске — в `README.md`.

## Что это

Сайт салона красоты в Гродзиск-Мазовецки, [placeof.beauty](https://placeof.beauty).
Язык сайта — польский. Все тексты, заголовки и разметка пишутся по-польски.

- `frontend/` — React 19, Create React App через craco, Tailwind, react-router 7,
  react-helmet-async. Роутинг в `src/App.js`.
- `backend/` — FastAPI + MongoDB. Отдаёт услуги, отзывы, галерею, контент главной,
  плюс админку на `/admin`.

## Жёсткое правило: локально = GitHub = VPS

Всё, что делается по проекту, живёт в трёх местах, и они не должны расходиться:

1. **Локально** — рабочая копия `/Users/artak/PlaceOfBeauty`.
2. **GitHub** — ветка `main` в `artak777gsm-lang/PlaceOfBeauty`. Репозиторий
   **публичный**.
3. **VPS** — `103.228.168.172`, каталог `/var/www/placeof.beauty`. Отсюда живёт
   placeof.beauty.

**Правка считается сделанной только тогда, когда доехала до всех трёх.**
Закоммитить локально и на этом остановиться — работа не сделана. Запушить в
`main` без выката — работа не сделана.

Порядок всегда один, потому что VPS тянет код из GitHub, а не из локальной копии:

```bash
git add -A && git commit -m "..."                                        # 1. локально
git checkout main && git merge --ff-only <ветка> && git push origin main # 2. GitHub
ssh root@103.228.168.172 'cd /var/www/placeof.beauty && bash update.sh'  # 3. VPS
```

Что из этого следует:

- **Незамерженная ветка — незавершённая работа.** Работать в отдельной ветке
  можно, но пока её нет в `main`, на боевом сайте её тоже нет.
- **Локальный `yarn build` обязателен перед пушем в `main`.** `update.sh`
  собирает фронт прямо на сервере: сломанный `main` — сломанный боевой сайт.
- **На сервере руками ничего не правим.** VPS только потребляет `main`; всё,
  что там изменено локально, снесёт следующий `git pull`. Исключение — данные:
  каталог `uploads/` и MongoDB живут вне репозитория и переживают пересборку.
- **Секретов в репозитории нет и быть не может** — он публичный. Пароли, ключи
  и доступы к серверу передаются вне гита, `.env` не коммитится.
- **После выката проверяем факт, а не намерение**: что на placeof.beauty
  отдаётся именно то, что собирали, а не прошлая сборка из кеша.

## Команды

```bash
cd frontend
yarn start        # дев-сервер, http://localhost:3000
yarn build        # craco build + пререндер
yarn prerender    # только пререндер, поверх уже собранного бандла
```

Фронтовых тестов нет. Бэкенд проверяется скриптами в корне: `backend_test.py`,
`gallery_path_test.py`.

Бэкенд для разработки фронта не нужен: страницы статичные, из API берутся только
прайс на `/uslugi` и контент главной. Без него подставляются захардкоженные
дефолты — в частности, на главной вместо залитого фото появляется сток с
Unsplash (`src/pages/Home.js:35`). Это ожидаемо, а не поломка.

## SEO — здесь легко сломать незаметно

Сайт продвигается по локальным запросам, и почти вся работа последних правок —
именно про поисковую выдачу. Три вещи, которые нужно держать в голове.

### Пререндер

CRA отдаёт один `index.html` на все URL, поэтому до исполнения JS краулер видел
на каждой странице заголовок и описание главной. `frontend/scripts/prerender.js`
после сборки обходит маршруты **из `public/sitemap.xml`** headless-браузером и
раскладывает готовый HTML по `build/<маршрут>/index.html`. Nginx подхватывает их
через `try_files $uri/index.html $uri /index.html`.

Порядок здесь значимый: `$uri/index.html` должен проверяться первым. Если первым
стоит `$uri`, nginx находит созданный пререндером каталог и отвечает 301 с
дописанным слешем. URL в `sitemap.xml`
и все `canonical` идут без слеша — то есть редирект получала бы каждая
проиндексированная страница, а конечная страница объявляла бы canonical на тот
адрес, с которого её только что увели. Конфиг генерируется из `update.sh`
и `deploy.sh`, правится там.

Отсюда следует: **новая страница появится в пререндере, только если добавить её
в `public/sitemap.xml`.** Список маршрутов берётся оттуда, а не из роутера.

Скрипт ждёт появления `<h1>` — у каждой страницы он ровно один, а у заглушки
загрузки его нет. Если страница не отрендерилась, остаётся SPA-заглушка и в лог
уходит предупреждение; сборка при этом не падает никогда.

### Разметка: сущность салона объявляется один раз

`BeautySalon` со всеми свойствами — адрес, гео, часы, `aggregateRating` —
объявлен **ровно один раз**, в `frontend/public/index.html`, и попадает на все
страницы. Google склеивает узлы по `@id` (`https://placeof.beauty/#salon`).

Страницы **не описывают салон заново**, а ссылаются на него через `salonRef()`
из `src/lib/seoSchema.js`. Если продублировать там `aggregateRating`, Search
Console выдаст «Multiple aggregate ratings assigned to review» — это уже
чинили в `d9bb969`.

Прайс-каталог (`hasOfferCatalog`) живёт только на главной,
`src/pages/Home.js` → `OFFER_CATALOG_JSON_LD`. Раньше он стоял в `index.html` и
уходил на все URL, из-за чего `/uslugi/piercing` объявляла офферы депиляции.

Проверка после правок разметки — все блоки должны парситься, и на каждой
странице должен быть ровно один `aggregateRating`:

```bash
cd frontend && yarn build
grep -c aggregateRating build/uslugi/piercing/index.html
```

### Заголовки и описания

Задаются компонентом `src/components/SEO.js` через react-helmet-async. У каждой
страницы должны быть свои. Мета `keywords` Google игнорирует — на ранжирование
она не влияет, менять её ради позиций смысла нет.

## Деплой

`deploy.sh` — первичная установка, `update.sh` — обновление; оба разворачивают
ветку `main` (см. правило трёх точек выше). `update.sh` дотягивает `main`,
пересобирает фронт и бэк, переписывает конфиг nginx и перезапускает сервис.

Конфиг nginx генерируется скриптами, а не правится на сервере. `update.sh`
перезаписывает `sites-available/placeof.beauty` и следит, чтобы
`sites-enabled/placeof.beauty` был симлинком на него: когда там оказывается
обычная копия, nginx читает её, правки из скрипта не применяются, и понять это
можно только по тому, что `nginx -t` проходит, а поведение не меняется.

**Node на сервере — не ниже 22.** `puppeteer` требует `>= 22.12`, и `yarn`
падает на несовместимом engine ещё до сборки: код при этом уже подтянут, а
пересборки нет, то есть сайт остаётся на прошлой сборке. Планка зашита в
`deploy.sh`.

`puppeteer` в devDependencies тянет свой Chromium (~180 МБ) при `yarn install`.
На сервере с тесным диском ставится системный Chromium плюс
`PUPPETEER_SKIP_DOWNLOAD=true` — скрипт сам найдёт бинарник.
